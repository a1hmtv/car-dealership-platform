# Car Dealership - микросервисная система автосалона

## 🎯 Цель работы

Разработать backend-систему мультибрендового автосалона, обеспечивающую управление автомобилями, складскими запасами, клиентскими заказами и заявками на тест-драйв. Реализовать конфигуратор автомобилей, ролевую модель доступа и межсервисное взаимодействие.

---

## 📦 Основные компоненты

1. **OrderService - управление заказами**
   - Оформление покупки автомобилей в наличии.
   - Заказ автомобилей с индивидуальной комплектацией.
   - Создание и обработка заявок на тест-драйв.
   - Автоматическое назначение менеджера на заказ.
   - Управление жизненным циклом заказов.

2. **StorageService - управление складом**
   - Управление каталогом автомобилей и запчастей.
   - Учёт складских остатков и резервирование комплектующих.
   - Проверка доступности автомобилей.
   - Создание и обработка внутренних заказов на сборку.
   - Предоставление информации об автомобилях в наличии через gRPC.

3. **Car Configurator - конфигуратор автомобилей**
   - Выбор индивидуальной комплектации автомобиля.
   - Проверка совместимости комплектующих с выбранной моделью.
   - Валидация обязательных компонентов.
   - Автоматический расчёт итоговой стоимости.

4. **Security - безопасность системы**
   - Централизованная аутентификация через Keycloak.
   - Авторизация на основе ролей пользователей.
   - Защита REST-эндпоинтов через Spring Security.
   - Проверка принадлежности заказов через `@PreAuthorize`.

---

## 👥 Роли пользователей

- **USER** - просмотр автомобилей, настройка комплектации, оформление заказов и запись на тест-драйв.
- **MANAGER** - управление клиентскими заказами и заявками на тест-драйв.
- **WAREHOUSE_ADMIN** - управление автомобилями, запчастями, складскими остатками и заказами на сборку.
- **ADMIN** - полный доступ ко всем операциям системы.

## ⚙️ Межсервисное взаимодействие

**Асинхронное взаимодействие:**

1. После оплаты заказа `OrderService` публикует событие `OrderSentForApproval`.
2. `StorageService` проверяет наличие автомобиля и необходимых комплектующих.
3. Склад выполняет резервирование или сборку автомобиля.
4. Публикуется событие `OrderApproved` или `OrderRejected`.
5. `OrderService` обновляет статус клиентского заказа.

**Синхронное взаимодействие:**

- `OrderService` запрашивает актуальные складские данные через gRPC у `StorageService`.
- Клиент получает информацию через REST API.
- При недоступности складского сервиса возвращается `503 Service Unavailable`.

## 🚫 Особенности реализации

- Микросервисная архитектура с независимыми базами данных.
- Соблюдение принципов ООП и разделение ответственности.
- Использование DTO для взаимодействия через REST API.
- Реализация Outbox Pattern для надёжной публикации событий.
- Идемпотентность обработки сообщений.
- Сквозное логирование через `traceId`.
- Поддержка Soft Delete.
- Покрытие unit-тестами более 70%.
- Обработка ошибок и таймаутов межсервисных вызовов.
